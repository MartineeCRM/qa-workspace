# 택소노미 Studio — 설계

## 배경

지금 qa-workspace의 택소노미는 대부분 파일(CSV/JSON/YAML) 업로드로 채워진다. 택소노미를
처음부터 제대로 설계하는 전용 화면을 만들고, 거기서 이미지 첨부·일괄 수정·검증 규칙 설정까지
지원하자는 아이디어에서 출발했다.

브레인스토밍 결과, 이건 새 제품이 아니라 **지금 qa-workspace 레포 안에 새 라우트를 하나
추가하는 일**로 정리됐다. 별도 레포·별도 DB로 분리하면 이미 존재하는 기능(같은 이름
프로퍼티를 여러 이벤트에 한번에 반영하는 로직 등)을 두 곳에서 유지보수해야 해서, 그 비용이
분리로 얻는 이득보다 크다고 판단했다.

## 범위

- **대상 사용자**: Martinee 내부팀만 (고객사 직접 접근 아님)
- **위치**: 같은 레포, 같은 Supabase 프로젝트, 같은 Vercel 배포. `/share/$token`처럼 워크스페이스
  사이드바 바깥의 독립된 라우트로 만들되, 인증은 기존 `/_authenticated` 가드를 그대로 쓴다
  (고객 포털용 커스텀 헤더를 새로 만들 필요 없음).
- **이름**: "Studio" — qa-workspace 쪽 링크 문구는 "Studio에서 편집"으로 통일한다.

## 아키텍처

새 라우트 2개, 기존 컴포넌트 재사용:

```
src/routes/_authenticated/taxonomy-studio/
  index.tsx        # 워크스페이스 → 프로젝트 선택 화면 (진입점)
  $projectId.tsx    # 기존 TaxonomyPage와 같은 구성 (TaxonomyTab + RulesTab)
```

- `index.tsx`: 기존 `useProjects(workspaceId)` 등 워크스페이스/프로젝트 조회 훅을 그대로 써서
  내가 접근 권한 있는 프로젝트 목록을 보여주고, 고르면 `$projectId`로 이동한다. qa-workspace를
  거치지 않고 `/taxonomy-studio`로 바로 들어올 수 있다.
- `$projectId.tsx`: 지금 `/taxonomy` 라우트가 쓰는 `TaxonomyTab`, `RulesTab`, `TaxonomyImport`
  컴포넌트를 **그대로 import**한다. 구조·규칙·파일 업로드(마이그레이션용) 기능을 새로 만들지
  않는다 — sibling-cascade 일괄 수정 로직도 여기 포함되어 그대로 따라온다.
- 별도 sync 파이프라인 없음. 두 라우트가 같은 테이블을 직접 읽고 쓴다. 단, 실시간 구독
  (`postgres_changes` 등)은 없으므로 "즉시 반영"은 아니다 — 한쪽에서 고친 내용은 다른 쪽을
  다시 불러오거나 재방문해야 보인다. 이미 열려있는 탭에 실시간으로 뜨진 않는다.

## 데이터 모델 변경

새 테이블은 만들지 않는다. `taxonomy_events`에 컬럼 하나만 추가한다:

```sql
alter table public.taxonomy_events
  add column trigger_screenshots jsonb not null default '[]'::jsonb;
  -- Storage 오브젝트 경로 문자열의 배열. 표시 순서 = 배열 순서(업로드 순).
  -- 별도 정렬 컬럼은 만들지 않는다 — 재정렬 UI가 실제로 필요해지면 그때 추가한다.
```

**동시 수정 주의**: 클라이언트가 배열 전체를 읽고 통째로 다시 쓰면(read-modify-write), 두
사람이 거의 동시에 이미지를 추가할 때 나중에 저장한 쪽이 먼저 저장된 걸 덮어쓸 수 있다. 이걸
피하려면 추가/삭제를 클라이언트에서 배열 전체를 조립하지 않고 DB에서 원자적으로 처리한다 —
추가는 `update ... set trigger_screenshots = trigger_screenshots || '["새경로"]'::jsonb`,
삭제는 경로 값으로 필터링해서 제거하는 식. 별도 테이블로 바꿔야 하는 이유(캡션·재정렬 등)는
아직 없지만, 이 동시성 처리는 컬럼 방식을 유지하는 조건으로 구현 계획에 반드시 포함한다.

기존 `te_select`/`te_update` RLS 정책이 컬럼 단위가 아니라 row 단위라 별도 정책 추가가 필요
없다.

Storage 버킷 하나 신설: `taxonomy-event-images`
- 경로 규칙: `{project_id}/{event_id}/{uuid}-{filename}`
- RLS는 기존 `is_ws_member(ws_of_project(...))` / `can_edit_ws(...)` 헬퍼를 그대로 재사용한다.
  단, 이 헬퍼들의 실제 경계는 **워크스페이스 단위**다 — 같은 워크스페이스의 다른 프로젝트
  멤버도 이 경로를 읽을 수 있다. "다른 프로젝트끼리 격리된다"는 뜻이 아니라 "이 프로젝트가
  속한 워크스페이스 밖의 사람은 못 본다"는 뜻으로 정정한다. 실제 `storage.objects` 정책 SQL은
  아직 안 썼고, 구현 계획 단계에서 작성한다.
- 이미지 저장 수명주기(생성 전 이벤트에 어떻게 붙일지, 이벤트/이미지 삭제 시 Storage 정리,
  업로드 형식·크기·장수 제한, 뷰어 화면)도 구현 계획 단계에서 정한다 — 이번 문서는 컬럼·버킷
  존재 여부까지만 정하고 상세 흐름은 아직 비워둔다.

## 기능 범위

1. **이벤트·프로퍼티·어트리뷰트 CRUD** — `TaxonomyTab` 그대로, 같은 이름 프로퍼티 일괄 수정
   포함.
2. **검증 규칙 설정** — `RulesTab` 그대로 (`validation_rules` / `validation_rule_targets`).
3. **이벤트 이미지 첨부 (신규)** — `EventDialog`에 여러 장 업로드/삭제 UI를 추가한다. 이벤트
   전용이며 (프로퍼티·어트리뷰트엔 안 붙음), "어느 화면에서 무슨 액션으로 발생하는 이벤트인지"
   설명하는 용도. 이 컴포넌트는 qa-workspace `/taxonomy`와 Studio 양쪽에서 같이 쓰이므로, 한
   군데 추가로 두 화면 모두에서 이미지 첨부가 가능해진다.
4. **파일 업로드(CSV/JSON/YAML) 마이그레이션** — `TaxonomyImport` 그대로, 초기 이관용으로
   Studio에도 유지한다.

## 상호 링킹

- qa-workspace `/taxonomy` 페이지 헤더에 "Studio에서 편집" 버튼 추가 → 같은 `projectId`로
  `/taxonomy-studio/$projectId` 딥링크.
- Studio `$projectId` 페이지에 "QA 현황 보기" 버튼 추가 → 같은 프로젝트의 qa-workspace
  `/taxonomy` (또는 프로젝트 홈)로 돌아가는 링크.

## 권한

새 권한 체계를 만들지 않는다. 기존 `canEdit(role)` (owner/admin/editor)를 그대로 적용한다 —
멤버가 아니면 애초에 프로젝트 선택 화면에 안 뜬다.

## 코덱스 리뷰 반영 (2026-09-21)

이 스펙과 브레인스토밍 핸드오프를 코덱스에게 리뷰시켰다. 지적 12개 중 코드로 직접 확인해서
검증한 결과를 반영한다.

**이번에 같이 고치기로 한 기존 버그** (Studio가 `TaxonomyTab`/`RulesTab`을 그대로 재사용하는
이상, 아래는 지금 `/taxonomy`에도 이미 있는 버그라 Studio를 만들기 전에 고쳐야 둘 다 안전
하다):

- **규칙 저장이 원자적이지 않다** (`rules-tab.tsx:341-357`). 기존 대상을 삭제하고 새 대상을
  삽입하는 게 별개의 요청 두 개다. 삭제는 성공하고 삽입이 실패하면 "대상 없는 규칙"이 남고,
  화면은 이를 "프로젝트 전체 적용"으로 읽는다. 두 요청을 하나의 DB 함수(RPC)로 묶어 원자적으로
  처리하도록 고친다.
- **채널 제외 설정이 로딩 레이스에 취약하다** (`taxonomy-tab.tsx:120`, `TaxonomyAttributeDialog`
  의 `selectedChannelIds` 초기화). `channels` 조회가 끝나기 전에 편집창을 열면 선택 상태가 빈
  값으로 고정되고, 그 상태로 저장하면 기존 제외 설정이 전부 "제외됨"으로 덮어써질 수 있다.
  `channels`/`excludedKeys`가 로딩 중일 때 다이얼로그를 못 열게 막거나, 로딩 완료 시
  `selectedChannelIds`를 다시 계산하도록 고친다.
- **로그인 후 원래 딥링크로 안 돌아간다** (`_authenticated/route.tsx:8`,
  `redirect: undefined`로 고정). Studio의 핵심 가치가 "링크 하나로 바로 진입"인데, 로그아웃
  상태에서 그 링크를 열면 로그인 후 엉뚱한 기본 화면으로 간다. 현재 경로를 `redirect` 파라미터
  로 넘기고 로그인 성공 후 그리로 보내도록 고친다.
- **CSV 파싱이 따옴표로 감싼 멀티라인 값을 깨뜨린다** (`taxonomy-import.ts:124`, 줄바꿈 기준
  단순 split). 제대로 된 CSV 파서로 교체하거나(패키지 미설치 상태라 구현 계획에서 검토), 최소
  한 이 제약을 가져오기 UI 안내 문구에 명시한다. 알 수 없는 데이터 타입이 조용히 `string`으로
  바뀌는 것(`:71`)도 가져오기 결과 요약(toast)에 "타입을 인식 못해 string으로 등록한 항목 N개"
  로 드러내기로 한다 — 조용히 넘어가지 않는다.

**현행 그대로 두기로 한 것** (검토했지만 고치지 않기로 확정):

- **같은 이름 프로퍼티 일괄 수정이 폼 전체(7개 필드)를 통째로 덮어쓰는 것.** 미리보기·필드
  단위 선택 같은 안전장치는 지금 추가하지 않는다 — "일괄 수정" 기능의 의도된 동작으로 보고,
  실제로 문제가 생기면 그때 안전장치를 고려한다.
- **"내부팀 전용"이 코드로 강제되지 않는 것.** 새 권한 체계를 안 만들기로 이미 브레인스토밍
  에서 정했으므로, 워크스페이스 멤버 = 내부팀이라는 전제를 그대로 신뢰한다.
- **`TaxonomyImport`를 별도로 다시 마운트하는 것처럼 보였던 우려.** 실제로는
  `TaxonomyTab`(`:293`) 안에 이미 포함돼 있어서, `<TaxonomyTab>`을 통째로 재사용하는 이번
  계획대로면 중복이 생기지 않는다. 별도 조치 불필요.

**여전히 열려 있고 구현 계획에서 채워야 하는 것**: 이미지 저장 수명주기(생성 전 이벤트에 업로드
연결, 삭제 시 Storage 정리), Storage RLS 정책 SQL, 이미지 동시 추가/삭제의 원자적 처리(위
데이터 모델 섹션에 방향 명시), 이미지 뷰어 화면과 업로드 제한(형식·크기·장수), `$projectId`
직접 진입 시 role 조회 방법(`useMyMemberships()` 활용, 워크스페이스 목록 화면과 동일한 데이터
소스).

## 범위 밖 (이번엔 안 함)

- 별도 레포/별도 Vercel 프로젝트로 분리
- 별도 DB + sync/export API
- 고객사(클라이언트) 직접 접근
- 이미지 재정렬 UI, 프로퍼티·어트리뷰트 이미지 첨부
- 새로운 권한 모델

## 테스트 관점

- `trigger_screenshots` 컬럼 추가는 마이그레이션 테스트(`supabase/tests/`)에 기본값 `[]`
  확인 케이스 추가.
- Storage 버킷 RLS는 "같은 워크스페이스의 다른 프로젝트 멤버는 읽을 수 있지만, 다른
  워크스페이스 사람은 못 읽는다"는 실제 경계 기준으로 케이스를 확인한다 (project 단위 격리가
  아님에 주의).
- 규칙 저장 원자성 수정은 "삽입 단계에서 강제로 실패시켜도 기존 대상이 사라지지 않는다"는
  케이스를 추가한다.
- 채널 제외 설정 수정은 "채널 목록 로딩 전에 다이얼로그를 열고 저장해도 기존 제외 설정이
  안 지워진다"는 케이스를 추가한다.
- CSV 파싱 수정은 따옴표로 감싼 멀티라인 값이 포함된 샘플로 회귀 테스트를 추가한다.
- `$projectId.tsx`가 `TaxonomyTab`/`RulesTab`을 그대로 마운트하므로, 기존 `taxonomy-tab`
  관련 테스트가 회귀 없이 통과하는지 확인한다 — 단, 이 테스트들은 import 파서·저장 테스트
  뿐이라 새 라우트·권한·이미지 실패 경로는 별도로 테스트를 채워야 한다 (새 컴포넌트 UI
  테스트까지는 불필요).

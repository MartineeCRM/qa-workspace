# QA Workspace 제품 및 기술 구조

이 문서는 제품 구조를 변경한 이유와 시스템이 검증 근거를 저장·판정하는 방식을 설명합니다. 화면에서 실제 QA를 수행하는 순서는 [사용자 가이드](USER_GUIDE.md)를 참고하세요.

## 1. 구조를 변경한 이유

기존 QA의 가장 큰 문제는 판정에 필요한 정보 일부가 시스템에 남지 않았다는 점입니다. Event User Log에 들어온 로그만으로는 “테스터가 실행했는데 수집되지 않은 것”과 “애초에 실행하지 않은 것”을 구분할 수 없었습니다. Custom Attribute 변경도 Query Builder 로그에 남지 않아 이벤트와 함께 검증할 근거가 부족했습니다.

현재 구조는 이 두 가지 관측 공백을 메우는 것에서 출발했습니다.

| AS-IS의 정보 공백                                      | 발생하던 문제                                                  | TO-BE에서 추가한 구조            | 얻는 효과                                            |
| ------------------------------------------------------ | -------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------- |
| 이벤트를 실행했다는 사실을 테스터만 알고 있었음        | 로그가 없을 때 미수집인지 미실행인지 판별할 수 없음            | 실행 항목 체크리스트와 실행 시각 | 체크했지만 CSV에 없는 이벤트를 미수집 후보로 탐지    |
| Custom Attribute 변경이 Query Builder 로그에 남지 않음 | 이벤트 이후 값이 실제로 바뀌었는지 확인할 근거가 없음          | Braze Attribute API 스냅샷       | 특정 시점의 어트리뷰트 값과 전후 변화를 저장·비교    |
| 이벤트 로그와 어트리뷰트 확인 위치가 달랐음            | 같은 사용자 행동에서 나온 결과인지 연결하기 어려움             | 검증 실행 단위의 병합 타임라인   | 이벤트 발생과 어트리뷰트 변화를 시간순으로 함께 확인 |
| 오류 여부와 업무 처리 상태가 한 흐름에 섞임            | 아직 논의하지 않은 오류와 개발이 확인한 이슈를 구분하기 어려움 | 판정 결과와 이슈 워크플로우 분리 | 미확인 오류, 확인된 이슈, 수정, 재검증을 구분        |
| 플랫폼별 검증 범위가 명시되지 않음                     | iOS만 완료해도 전체가 완료된 것처럼 보일 수 있음               | 필수 검증 채널과 채널별 실행     | Android, iOS 등 필요한 채널을 각각 커버리지에 반영   |

따라서 체크리스트는 단순한 할 일 목록이 아닙니다. **로그에 나타나지 않는 테스터의 실행 사실을 데이터로 만드는 장치**입니다. 스냅샷도 화면을 저장하는 부가 기능이 아니라, **기존 로그 시스템이 제공하지 않는 Custom Attribute 상태를 검증 근거로 만드는 수집 방식**입니다.

## 2. AS-IS: 관측 정보가 부족한 항목별 동기식 검증

기존 업무는 택소노미를 한꺼번에 실행한 뒤 나중에 검토하는 방식이 아니었습니다. 테스터가 택소노미 항목 하나를 선택하고 아래 사이클을 완료한 뒤 다음 항목으로 넘어갔습니다.

```text
택소노미 항목 선택
        ▼
앱에서 이벤트 실행
        ▼
Event User Log 반영 대기
        ▼
해당 로그 검색 및 값 대조
        ▼
이슈 여부 체크
        ▼
다음 택소노미 항목 선택
```

이 방식은 실행 직후 로그를 확인하므로 개별 항목의 맥락은 분명하지만 다음 한계가 있었습니다.

- 로그 반영 대기 시간이 매 항목의 작업을 막았습니다.
- 로그가 나타나지 않으면 미수집과 미실행을 구분할 수 없었습니다.
- 실행 여부를 테스터의 기억과 수기 기록에 의존했습니다.
- Custom Attribute는 Query Builder 로그만으로 변경 여부를 확인할 수 없었습니다.
- 이벤트 실행과 어트리뷰트 API 반영 시점이 달라 한 흐름으로 비교하기 어려웠습니다.
- 택소노미, Event User Log, 이슈 기록 사이를 항목마다 반복해서 이동해야 했습니다.
- 실행한 사실, 실제 수집 근거, 판정, 후속 논의가 하나의 작업 단위로 연결되지 않았습니다.
- 플랫폼과 라운드가 늘어나면 완료 범위와 재검증 대상을 한눈에 집계하기 어려웠습니다.

## 3. TO-BE: 실행 사실과 상태 변화를 먼저 기록

현재 구조는 기존 사이클의 순서를 없애는 것이 아니라, 서로 다른 대기 시간과 책임을 가진 단계를 분리합니다.

| 기존 한 항목의 작업      | 현재 단계                   | 분리한 이유                                    |
| ------------------------ | --------------------------- | ---------------------------------------------- |
| 택소노미 확인과 앱 실행  | 실행 항목 체크리스트        | 실행 사실과 시각을 남겨 미수집 판정에 사용     |
| Event User Log 반영 대기 | 수집 대기 중 다른 항목 실행 | 대기 시간 때문에 전체 QA가 멈추지 않도록 함    |
| 어트리뷰트 변화 확인     | Attribute API 스냅샷        | Query Builder에 없는 상태와 변화를 근거로 저장 |
| 로그 검색과 값 대조      | CSV·스냅샷 병합 분석        | 같은 실행의 근거를 한곳에서 시간순으로 비교    |
| 오류 여부 판단           | 규칙 기반 판정 후 AI 보조   | 확정 가능한 오류와 의미 판단을 분리            |
| 이슈 체크와 전달         | 이슈 모아보기               | 논의·개발 수정·재검증을 판정 화면과 분리       |

```text
여러 항목을 실행하며 즉시 체크
             │
             ├─ 어트리뷰트 반영 대기 후 스냅샷
             └─ Event User Log CSV 수집
                         ▼
                 시간순 병합 및 분석
                         ▼
                   사람의 결과 검토
                         ▼
               이슈 논의·수정·재검증
```

여기서 “여러 항목을 실행”은 택소노미 확인을 생략한다는 뜻이 아닙니다. 검증 실행 화면의 왼쪽에 택소노미를 계속 보여주고, 테스터가 실제 행동을 수행할 때마다 바로 체크합니다. 분리의 핵심은 **로그 반영을 기다리는 시간을 실행 작업과 분리하는 것**입니다.

### 미수집을 판정할 수 있게 된 과정

```text
테스터가 이벤트를 실행하고 체크
              │
              ▼
체크리스트에 대상과 실행 시각 저장
              │
              ▼
Event User Log CSV에서 같은 이벤트 검색
        ┌─────┴─────┐
        ▼           ▼
     발견됨       발견되지 않음
        │           │
        ▼           ▼
 값·형식 분석    미수집 후보 안내
                    │
                    ▼
       로그 반영 지연 재확인 후 미발생 판정
```

체크리스트가 없으면 CSV에 없는 이벤트는 검증 대상이 아니었는지, 실행했지만 누락된 것인지 알 수 없습니다. 체크리스트가 기대값 역할을 하면서 `실행 기록 - 실제 수집 기록`의 차이를 계산할 수 있게 됐습니다.

### Custom Attribute를 검증할 수 있게 된 과정

```text
이벤트 실행 및 체크
        │
        ▼
연관 Custom Attribute와 반영 지연 안내
        │
        ▼
Braze Attribute API로 사용자 상태 촬영
        │
        ▼
스냅샷 값과 촬영 시각 저장
        │
        ▼
이벤트 로그와 시간순 병합
        │
        ▼
타입·형식·의미와 이벤트 전후 변화 분석
```

스냅샷은 “변경 이벤트 로그”를 새로 만들어내는 것이 아닙니다. 여러 시점의 사용자 상태를 저장하고 이전 스냅샷과 비교해 어떤 값이 추가·변경됐는지를 계산합니다. 이 방식으로 Query Builder에 남지 않던 Custom Attribute도 검증 범위에 포함됩니다.

## 4. 제품 구조

```text
워크스페이스
├─ 멤버와 권한
└─ 프로젝트 (고객/서비스 단위)
   ├─ 택소노미 (모든 QA 환경의 단일 기준)
   │  ├─ 이벤트
   │  │  └─ 프로퍼티
   │  ├─ 커스텀 어트리뷰트
   │  └─ 검증 규칙
   ├─ 검증 채널 (Android, iOS, Web ...)
   ├─ QA 환경 (개발 QA, 운영 QA ...)
   │  └─ 라운드
   │     └─ 검증 실행
   │        ├─ 실행 체크리스트
   │        ├─ Event User Log CSV
   │        ├─ 어트리뷰트 스냅샷
   │        └─ 판정 결과
   └─ 이슈 모아보기
      ├─ 대상별 상태
      └─ 댓글 이력
```

핵심 원칙은 택소노미를 환경이나 채널마다 복제하지 않는 것입니다. 같은 키는 같은 타입과 의미를 가지며, 특정 채널에서 수집하지 않는 항목만 채널 제외 정보로 표현합니다.

## 5. 화면 구조

프로젝트 안의 상단 탭은 다음 책임을 가집니다.

| 화면          | 책임                                                  |
| ------------- | ----------------------------------------------------- |
| 개요          | 현재 택소노미 기준의 환경·채널별 커버리지와 이슈 현황 |
| 이슈 모아보기 | 확인된 이슈의 댓글, 상태, 다음 차수 제출 관리         |
| QA 환경 탭    | 라운드와 채널별 검증 실행 관리                        |
| 택소노미      | 이벤트·프로퍼티·어트리뷰트와 AI 판단 기준 관리        |

한 검증 실행 화면은 `검증 실행 → 분석 → 결과`의 3단계로 구성됩니다. 단계 전환은 별도 데이터를 복사하는 작업이 아니라 동일한 실행에 로그와 결과가 차례로 쌓이는 과정입니다.

## 7. 분석 데이터 흐름

```text
사용자가 체크한 실행 대상
          │
          ├─────────────┐
          ▼             ▼
Event User Log CSV   Braze Attribute API
          │             │
          ▼             ▼
   이벤트 원본 행    어트리뷰트 스냅샷
          └──────┬──────┘
                 ▼
          시간순 병합 데이터셋
                 ▼
       규칙 기반 형식·수집 검증
                 ▼
        의미 판단이 필요한 항목
                 ▼
          OpenAI 기반 AI 검증
                 ▼
       통과 / 오류 / 미발생 결과
                 ▼
        이슈와 댓글로 후속 관리
```

### 규칙 기반 검증

코드에서 확정적으로 판단할 수 있는 내용을 먼저 처리합니다.

- 실행 대상의 로그 존재 여부
- 필수 프로퍼티 누락
- 택소노미에 없는 프로퍼티 수신
- string, number, boolean, array, array of object 타입 불일치
- 명시된 enum이나 구조 규칙

### AI 검증

타입만으로 판단할 수 없는 의미와 표현을 보조적으로 확인합니다.

- 예시값과 실제 값의 의미 체계가 같은지
- URL, 국가 코드, 사람이 읽는 이름처럼 표현 방식이 어긋나는지
- 대소문자 차이가 의미 있는 오류인지
- 이벤트와 어트리뷰트의 시간 관계가 규칙 설명에 맞는지

AI는 택소노미의 타입, 예시값, 설명과 연결된 검증 규칙을 근거로 사용합니다. 원문 로그를 그대로 응답 JSON에 인용하지 않고 구조화된 근거로 전달해 긴 배열이나 특수문자로 응답 파싱이 깨지는 위험을 줄입니다.

## 8. 시간 기준

- CSV 업로드 시각은 파일을 업로드한 시각입니다.
- 병합 데이터셋의 이벤트 시각은 CSV 원본의 발생 시각을 그대로 표시합니다.
- 어트리뷰트 스냅샷 시각은 촬영 시각을 한국 시간으로 표시합니다.
- 스냅샷 배열 내부의 `date` 같은 값은 데이터 자체의 값이며 촬영 시각과 별개입니다.

따라서 AI가 이벤트 발생 시각과 스냅샷 촬영 시각을 무조건 동일하다고 가정해서는 안 됩니다. 이벤트 이후 API 반영 지연과 촬영 대기 시간을 허용하고, 배열 정렬 방향도 택소노미나 규칙에 명시된 경우에만 오류로 판단합니다.

## 9. 이슈와 커버리지 구조

판정 결과와 이슈 상태는 서로 다른 책임을 가집니다.

- **판정 결과**는 특정 검증 실행에서 로그가 기준에 맞았는지 기록합니다.
- **이슈**는 그 결과를 사람이 확인하고 수정·재검증하기 위한 업무 상태입니다.
- 통과 결과에도 사람이 이슈를 등록할 수 있습니다.
- 다음 차수 제출은 과거 결과를 복사하는 것이 아니라 재검증할 대상을 전달합니다.

커버리지는 현재 택소노미와 필수 채널을 분모로 계산합니다. 환경 하나 또는 채널 하나만 끝났다고 전체 프로젝트가 100%가 되지 않도록 채널별 완료 여부를 구분합니다.

| 위치                                      | 역할                                            |
| ----------------------------------------- | ----------------------------------------------- |
| `src/routes`                              | TanStack Start 파일 기반 라우트와 페이지 진입점 |

## 11. 보안 경계

- 사용자는 Supabase Auth로 로그인합니다.
- 워크스페이스 역할과 Postgres RLS가 데이터 접근을 제한합니다.
- `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, Attribute API Key는 브라우저에 노출하면 안 됩니다.
- Attribute API Key는 저장 후 다시 읽어 화면에 표시하지 않습니다.
- 배포 환경마다 Supabase 프로젝트와 서버 환경변수를 분리합니다.

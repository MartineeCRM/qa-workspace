# QA Workspace 사용자 가이드

이 문서는 QA Workspace를 처음 여는 사람이 로그인부터 택소노미 등록, 첫 검증 결과 확인까지 순서대로 따라 할 수 있는 안내서입니다. 화면의 버튼 이름을 그대로 사용하므로 위에서부터 진행하면 됩니다.

## 어디부터 시작하나요?

처음 사용하는 경우 아래 순서로 진행합니다.

1. 회사 이메일로 가입하거나 로그인합니다.
2. 초대받은 워크스페이스를 선택합니다.
3. 고객 또는 서비스 단위의 프로젝트를 엽니다.
4. **택소노미**에서 기준 파일을 가져옵니다.
5. **QA 환경 관리**에서 환경과 검증 채널을 확인합니다.
6. QA 환경 탭에서 라운드와 검증 실행을 만듭니다.
7. 앱을 조작하며 이벤트를 체크하고 필요한 어트리뷰트 스냅샷을 촬영합니다.
8. Event User Log CSV를 업로드하고 분석합니다.
9. 결과를 검토하고 필요한 항목을 이슈로 등록합니다.

이미 워크스페이스, 프로젝트, 택소노미가 준비되어 있다면 6번부터 시작하세요. **새 워크스페이스** 또는 **새 프로젝트** 버튼이 보이지 않으면 권한이 없는 것이므로 관리자에게 생성을 요청합니다.

## 1. 이 도구로 무엇을 하나요?

QA Workspace는 “어떤 로그가 들어와야 하는가”와 “실제로 어떤 로그가 들어왔는가”를 비교합니다.

- **택소노미**: 모든 QA 환경이 함께 사용하는 이벤트·프로퍼티·어트리뷰트의 기준
- **검증 실행**: 한 채널에서 로그를 실행하고 분석해 결과를 만드는 한 사이클
- **이슈**: 분석 결과 중 사람이 확인하고 개발 수정까지 추적할 대상

제품에서 사용하는 용어는 다음과 같습니다.

| 용어       | 뜻                                         | 예시                                 |
| ---------- | ------------------------------------------ | ------------------------------------ |
| 이벤트     | 사용자의 행동 로그                         | `login_completed`, `item_viewed`     |
| 프로퍼티   | 이벤트에 딸려 들어오는 값                  | `referral_source`, `item_id`         |
| 어트리뷰트 | 사용자에게 누적되는 custom attribute       | `search_history`, `membership_grade` |
| QA 환경    | 개발 QA, 운영 QA처럼 검증 목적이 다른 공간 | 개발 QA, 운영 QA                     |
| 채널       | 같은 환경에서 별도로 검증해야 하는 플랫폼  | Android, iOS, PC Web                 |
| 라운드     | 1차, 2차처럼 수정과 재검증을 구분하는 단위 | 1차 검증, 수정 확인 2차              |

## 2. 전체 업무 흐름

이 문서는 현재 화면을 사용하는 순서만 설명합니다. 시스템 구성과 데이터 흐름은 [서비스 구조 설명](ARCHITECTURE.md)을 참고하세요.

```text
[준비]
워크스페이스 → 프로젝트 → 택소노미 → QA 환경/채널
                                      │
                                      ▼
[검증]
라운드 → 검증 실행 → ① 실행 체크/스냅샷 → ② CSV 대조/분석 → ③ 결과
                                                                  │
                                                                  ▼
[후속 처리]
이슈 등록 → 댓글/상태 변경 → 개발 수정 → 다음 차수 제출 → 재검증
```

처음 한 번만 준비 단계를 진행합니다. 이후에는 검증과 후속 처리를 라운드마다 반복합니다.

## 3. 로그인하고 프로젝트 열기

### 3.1 가입 또는 로그인

1. QA Workspace 로그인 화면을 엽니다.
2. 계정이 있다면 회사 이메일과 비밀번호를 입력하고 **로그인**을 누릅니다.
3. 계정이 없다면 **가입하기**를 누릅니다.
4. 회사 이메일, 6자 이상의 비밀번호, 비밀번호 확인을 입력하고 **가입하기**를 누릅니다.
5. 로그인되면 **워크스페이스** 목록으로 이동합니다.

가입 후 “접근 권한이 없어요”가 표시되면 오류가 아닙니다. QA Workspace는 초대받은 사용자만 이용할 수 있습니다. 워크스페이스 관리자에게 가입한 이메일 주소로 초대를 요청한 뒤 다시 로그인하세요.

### 3.2 워크스페이스 선택 또는 생성

워크스페이스는 여러 프로젝트와 함께 일하는 사용자를 묶는 최상위 공간입니다.

- 초대받은 워크스페이스가 있다면 목록에서 이름을 선택합니다.
- 플랫폼 관리자 또는 기존 워크스페이스 소유자라면 **새 워크스페이스**를 눌러 이름과 설명을 입력할 수 있습니다.
- 워크스페이스를 만든 사용자는 소유자가 됩니다.
- 팀원 초대와 권한 변경은 워크스페이스의 **설정**에서 진행합니다.

권한은 네 가지입니다.

| 권한   | 할 수 있는 일                          |
| ------ | -------------------------------------- |
| 소유자 | 모든 작업과 워크스페이스 삭제          |
| 관리자 | 멤버, 프로젝트, 워크스페이스 설정 관리 |
| 편집자 | 택소노미, 규칙, QA 결과 생성·수정      |
| 뷰어   | 읽기 전용 확인                         |

### 3.3 프로젝트 선택 또는 생성

프로젝트 하나를 고객 또는 서비스 하나의 QA 공간으로 사용합니다.

1. 워크스페이스에서 기존 프로젝트를 선택합니다.
2. 새로 만들어야 한다면 **새 프로젝트**를 누릅니다.
3. 프로젝트 이름을 입력합니다.
4. 워크스페이스 안에서 중복되지 않는 짧은 **프로젝트 키**를 입력합니다.
5. 필요하면 설명을 입력하고 **프로젝트 만들기**를 누릅니다.

프로젝트를 열면 상단에 **개요**, **이슈 모아보기**, QA 환경 탭, **택소노미**가 표시됩니다. 처음 설정할 때는 **택소노미**부터 시작합니다.

## 4. 택소노미 등록하기

### 4.1 택소노미 파일 준비

QA Workspace의 택소노미는 다음 구조를 사용합니다.

- 이벤트: 실제 행동 로그의 기술명, 표시명, 설명, 수집 시점
- 이벤트 프로퍼티: 이벤트에 포함되는 키, 타입, 필수 여부, 허용값
- 어트리뷰트: 사용자에게 누적되는 custom attribute의 키, 타입, 필수 여부, 허용값

일괄 등록은 CSV, JSON, YAML 파일을 지원합니다. Excel 파일은 직접 업로드할 수 없으므로 먼저 지원 형식으로 변환해야 합니다. 형식이 필요하면 **가져오기** 메뉴의 예시 데이터셋을 내려받아 기준으로 사용하세요.

### 4.2 파일로 일괄 등록

1. 프로젝트 상단에서 **택소노미**를 선택합니다.
2. **이벤트·프로퍼티·어트리뷰트** 화면인지 확인합니다.
3. 오른쪽의 **가져오기**를 누릅니다.
4. **파일로 일괄 등록**을 선택합니다.
5. 준비한 CSV, JSON 또는 YAML 파일을 선택합니다.
6. 완료 알림에서 새로 추가된 이벤트와 프로퍼티·어트리뷰트 수를 확인합니다.
7. 화면 상단의 이벤트, 이벤트 프로퍼티, 어트리뷰트 개수가 원본과 맞는지 확인합니다.

가져오기는 같은 기술명의 기존 항목을 덮어쓰지 않고 새 항목만 추가합니다. 기존 정의를 바꾸려면 해당 행을 열어 직접 수정하세요. 파일을 고친 뒤 다시 올렸는데 “새로 추가된 내용은 없어요”가 표시되는 것은 정상입니다.

### 4.3 등록 결과 점검

검색창에서 대표 이벤트와 어트리뷰트를 찾아 다음을 확인합니다.

- 기술명이 실제 로그 키와 정확히 일치하는가
- 이벤트 아래에 프로퍼티가 올바르게 연결됐는가
- `string`, `number`, `boolean`, `array`, `array of object` 타입이 맞는가
- 필수 프로퍼티가 **필수**로 설정됐는가
- enum처럼 허용값이 정해진 항목에 허용값이 들어갔는가
- 설명과 수집 시점만 읽어도 언제 어떤 값이 들어와야 하는지 알 수 있는가

필요한 항목이 빠졌다면 **추가**에서 이벤트나 어트리뷰트를 만들고, 이벤트 행의 메뉴에서 **프로퍼티 추가**를 선택합니다. 배열 객체형 어트리뷰트의 내부 구조는 어트리뷰트 상세에서 **필드 추가**로 정의합니다.

### 4.4 검증 규칙 추가

타입과 허용값만으로 판단할 수 없는 조건은 **검증 규칙** 화면에 등록합니다. 예를 들어 특정 이벤트 이후 어트리뷰트가 바뀌어야 하는 조건, 값의 의미, 다른 필드와의 관계를 설명합니다. 규칙은 AI 의미 검증의 근거가 되므로 기대 결과와 예외를 구체적으로 적습니다.

## 5. QA 환경과 연동 준비

### 5.1 QA 환경과 채널 설정

1. 프로젝트 상단의 **QA 환경 관리**를 누릅니다.
2. 개발 QA, 운영 QA 등 필요한 환경이 있는지 확인합니다.
3. 없다면 이름과 설명을 입력하고 **환경 추가**를 누릅니다.
4. **검증 채널 설정**을 눌러 Android, iOS, Mobile Web, PC Web 등 실제 검증 채널을 추가합니다.
5. 전체 커버리지에 반드시 포함할 채널은 **필수**를 켭니다.
6. 새 검증 실행에서 사용할 채널은 **사용**을 켭니다.

사용한 채널은 이력 보존을 위해 삭제하지 않고 **사용**을 끕니다. 특정 채널에서 원래 수집하지 않는 이벤트나 프로퍼티는 택소노미 항목의 **수집 채널** 설정에서 제외합니다.

### 5.2 어트리뷰트 API 설정

어트리뷰트를 검증할 프로젝트만 설정합니다.

1. 프로젝트 상단의 **Attribute API 설정**을 누릅니다.
2. Braze REST API 엔드포인트와 API Key를 입력합니다.
3. 저장 후 연결 상태를 확인합니다. `/users/export/ids` 경로는 자동으로 붙습니다.

API Key는 보안을 위해 저장 후 다시 표시되지 않습니다. 키를 바꾸려면 새 값을 다시 입력합니다.

## 6. 첫 검증 실행 만들기

1. 프로젝트 상단에서 검증할 QA 환경 탭을 선택합니다.
2. 라운드가 없다면 **+ 새 라운드 시작**을 누릅니다.
3. 라운드에서 **검증 채널 선택**을 열어 Android, iOS 등 이번 실행의 채널을 선택합니다.
4. 실행 목적을 알 수 있는 이름을 입력합니다. 예: `회원가입 시나리오`, `iOS 기본 수집`.
5. **+ 새 검증 실행**을 누릅니다.
6. 생성된 카드를 선택해 검증 실행 화면으로 들어갑니다.

라운드는 1차 검증, 수정 확인 2차처럼 재검증 차수를 구분합니다. 검증 실행은 한 채널에서 실행 기록, 분석, 결과를 만드는 한 사이클입니다.

## 7. 검증 실행하기

QA 환경 탭으로 들어가 라운드를 선택합니다. 필요하면 **새 라운드 시작**을 누르고, 채널별로 **새 검증 실행**을 만듭니다.

검증 실행 하나는 아래 세 단계로 진행됩니다.

### 7.1 1단계: 검증 실행

이 화면은 앱을 직접 조작하면서 실행 사실을 기록하는 곳입니다.

1. 왼쪽 택소노미에서 **이벤트** 또는 **어트리뷰트** 탭을 선택합니다.
2. 앱에서 행동을 실행한 직후 해당 항목을 체크합니다.
3. 이벤트를 펼쳐 기대 프로퍼티, 타입, 필수 여부와 설명을 함께 확인합니다.
4. 체크한 항목은 오른쪽 **실행 기록과 스냅샷** 영역에 쌓입니다.
5. 어트리뷰트 확인이 필요하면 Braze ID를 입력하고 스냅샷을 촬영합니다.

이벤트 실행 뒤 연결된 어트리뷰트가 갱신될 것으로 보이면 시스템이 스냅샷 촬영을 추천합니다. API 반영 시간을 고려해 약 1분 뒤 촬영하는 것이 기본 흐름이며, 급하면 **지금 촬영**을 사용할 수 있습니다.

잘못 체크했다면 다시 눌러 실행 기록에서 제거할 수 있습니다. 같은 이벤트를 다시 실행했다면 실행 시각도 다시 기록할 수 있습니다.

### 7.2 2단계: 분석

먼저 Braze Query Builder에서 이번 검증 실행의 Event User Log를 조회합니다. 아래 쿼리를 복사한 뒤 `user_id`, 조회 시작 시각, `platform`을 실제 검증 조건에 맞게 바꾸세요.

```sql
SELECT
    id AS event_id,
    user_id,
    CONVERT_TIMEZONE('UTC', 'Asia/Seoul', TO_TIMESTAMP(time)) AS time,
    name,
    properties
FROM USERS_BEHAVIORS_CUSTOMEVENT_SHARED
WHERE user_id = '6a71aed4771abc89cf55abf9'
  AND CONVERT_TIMEZONE('UTC', 'Asia/Seoul', TO_TIMESTAMP(time))
      >= '2026-08-12 00:00:00'::TIMESTAMP
  AND PARSE_JSON(properties):platform::STRING = 'ios_app'
ORDER BY time DESC;
```

변경할 값은 다음과 같습니다.

| 조건           | 변경 방법                                                          |
| -------------- | ------------------------------------------------------------------ |
| `user_id`      | 이번 QA에 사용한 사용자 ID로 변경합니다.                           |
| 조회 시작 시각 | 앱 테스트를 시작한 한국 시각보다 조금 이른 값으로 변경합니다.      |
| `platform`     | 검증 실행의 채널에 맞춰 `ios_app` 등의 실제 수집값으로 변경합니다. |

쿼리 결과에 이번에 실행한 이벤트가 포함됐는지 확인한 뒤 CSV로 내려받습니다. 다른 사용자의 로그나 이전 테스트 로그가 섞이지 않도록 사용자 ID와 시간 범위를 반드시 확인하세요.

내려받은 CSV를 QA Workspace에 업로드합니다. CSV에는 다음 컬럼이 필요합니다. 컬럼명의 대소문자는 구분하지 않습니다.

| 컬럼         | 필수 | 내용                               |
| ------------ | ---- | ---------------------------------- |
| `EVENT_ID`   | 필수 | 이벤트 로그의 고유 식별자          |
| `NAME`       | 필수 | 이벤트 이름                        |
| `TIME`       | 필수 | 이벤트 발생 시각                   |
| `USER_ID`    | 필수 | 사용자 식별자                      |
| `PROPERTIES` | 선택 | JSON object 형태의 이벤트 프로퍼티 |

예시:

```csv
EVENT_ID,NAME,TIME,USER_ID,PROPERTIES
evt-001,login_completed,2026-08-06T10:30:00+09:00,user-123,"{""platform"":""ios_app""}"
```

업로드 후 화면에서 다음을 확인합니다.

- **수집 확인**: 체크한 이벤트가 CSV에도 있음
- **미수집 후보**: 실행했다고 체크했지만 CSV에서 찾지 못함
- **추가 수집**: 체크하지 않았지만 CSV에서 발견됨

미수집 후보는 CSV 반영 지연일 수 있습니다. Event User Log에서 다시 확인하고 필요하면 CSV를 추가 업로드하세요. 그대로 분석하면 미발생으로 판정됩니다. 체크하지 않은 추가 수집 이벤트는 이번 검증 대상에 자동으로 포함되지 않습니다.

아래의 병합 데이터셋에서 이벤트 발생 기록과 어트리뷰트 스냅샷 변화를 시간순으로 확인한 뒤 **검증 결과 분석**을 누릅니다. 분석 중에는 진행 건수와 진행률이 표시됩니다.

### 7.3 3단계: 결과

결과는 다음 세 가지로 나뉩니다.

| 결과   | 뜻                                                         |
| ------ | ---------------------------------------------------------- |
| 통과   | 현재 택소노미와 규칙에 어긋나는 점을 찾지 못함             |
| 오류   | 필수 누락, 미정의 값, 타입 또는 값·형식 불일치 등을 발견함 |
| 미발생 | 실행 대상으로 기록했지만 분석할 로그나 스냅샷을 찾지 못함  |

목록에서 항목을 선택하면 상세 화면에서 다음을 볼 수 있습니다.

- 규칙 기반 분석과 AI 판정 요약
- 실제 수신값(AS-IS)과 택소노미 정의(TO-BE)의 대조
- 근거가 된 이벤트 로그와 어트리뷰트 변화
- 택소노미 수정, 구현 수정 요청, 재분석 같은 해소 방향

AI 결과는 보조 판단입니다. 의미가 애매하거나 보수적으로 표시된 항목은 근거 로그와 택소노미 설명을 함께 확인하세요. 통과한 항목도 사람이 문제를 발견하면 **이슈 있음**으로 등록할 수 있습니다.

## 8. 이슈 처리하기

결과 상세에서 문제 대상을 선택해 이슈로 등록하면 프로젝트의 **이슈 모아보기**에 나타납니다. 이벤트 전체 또는 특정 프로퍼티·어트리뷰트를 대상으로 등록할 수 있습니다.

이슈 상태는 다음 흐름으로 사용합니다.

```text
이슈 있음 → 논의중 → 개발 수정 중 → 해결 → 다음 차수 검증 목록 제출
```

- 새 메모 입력창에 댓글을 남깁니다.
- 가장 최근 메모는 바로 보이고, 이전 메모는 **기존 메모 보기**에서 확인합니다.
- 본인이 남긴 댓글은 수정할 수 있습니다.
- 이슈의 출처 환경, 채널, 검증 실행, 라운드와 리포팅한 사람을 함께 확인합니다.
- 실제 수정이 시작되면 **개발 수정 중**, 수정이 끝나면 **해결**로 바꿉니다.
- 개발 수정 중 또는 해결 상태의 항목만 선택해 다음 차수 검증 목록으로 제출합니다.
- 잘못 등록한 이슈는 삭제할 수 있습니다. 삭제하면 연결된 댓글도 함께 없어지므로 주의하세요.

다음 차수에서는 제출된 항목을 새 로그로 다시 검증합니다. 예전 로그를 새 판정의 근거로 간주하지 않습니다.

## 9. 개요와 커버리지 읽기

프로젝트 **개요**는 현재 택소노미를 기준으로 QA 환경과 필수 채널의 진행 상태를 보여줍니다. 택소노미를 바꾸면 과거에 고정된 숫자를 보여주는 것이 아니라 현재 기준으로 다시 계산됩니다.

라운드의 숫자는 중복 대상을 한 번만 셉니다.

- **검증 실행**: 이번 라운드에서 실제로 검증한 이벤트·어트리뷰트 수
- **통과**: 현재 결과가 통과인 대상 수
- **미확인 이슈**: 오류가 있지만 아직 이슈로 등록하지 않은 대상 수
- **확인된 이슈**: 오류가 있고 논의 대상으로 등록된 대상 수

프로퍼티 오류를 이벤트 전체 이슈로 등록했다면 해당 프로퍼티도 확인된 이슈로 봅니다.

## 10. 자주 생기는 질문

### 체크하지 않은 CSV 이벤트가 결과에 없는 이유는 무엇인가요?

CSV는 수집 사실을 보여주는 자료이고, 체크리스트는 이번에 검증하겠다고 확정한 범위입니다. 예상보다 오래된 항목이나 다른 테스트의 로그가 섞이는 것을 막기 위해 체크하지 않은 이벤트는 자동으로 분석 대상에 넣지 않습니다.

### 실행했는데 미발생으로 나오는 이유는 무엇인가요?

이벤트 이름이 택소노미와 정확히 일치하는지, CSV가 최신인지, 올바른 검증 실행에 업로드했는지 확인하세요. 어트리뷰트라면 스냅샷에 해당 키가 실제로 들어왔는지도 확인합니다.

### 같은 값이 어떤 때는 통과하고 어떤 때는 오류인 이유는 무엇인가요?

택소노미의 예시값과 설명, 연결된 검증 규칙, 분석 당시 수집된 근거가 다를 수 있습니다. 정의를 바꾼 뒤에는 **다시 분석**을 실행해야 현재 정의가 결과에 반영됩니다.

### AI 분석이 동작하지 않으면 무엇을 확인하나요?

운영자가 서버의 `OPENAI_API_KEY`, API 크레딧 잔액, `OPENAI_MODEL` 설정을 확인해야 합니다. 월간 spend limit은 잔액이 아니므로 크레딧 소진 오류와 구분해야 합니다.

## 11. 첫 검증 완료 체크리스트

첫 검증을 마치기 전에 아래 항목을 확인합니다.

- 올바른 워크스페이스와 프로젝트에서 작업했다.
- 택소노미 건수가 원본 파일과 일치한다.
- 이번 검증의 QA 환경과 채널이 맞다.
- 앱에서 실행한 이벤트를 빠짐없이 체크했다.
- 어트리뷰트가 필요한 경우 올바른 Braze ID로 스냅샷을 촬영했다.
- 최신 Event User Log CSV를 올렸다.
- 미수집 후보와 추가 수집 항목을 검토했다.
- 분석 결과의 AS-IS, TO-BE, 근거 로그를 확인했다.
- 실제 수정이 필요한 항목을 이슈로 등록했다.

## 12. 권장 운영 원칙

- 택소노미 변경 권한과 로그 판정 권한을 구분하지 말고, 변경 이유를 이슈 댓글에 남깁니다.
- Android와 iOS처럼 필수 채널은 각각 검증 실행을 만들고 모두 완료합니다.
- CSV 업로드 전후의 사용자 ID와 테스트 시각을 기록해 다른 테스트 로그가 섞이지 않게 합니다.
- AI 판정만 보고 수정하지 말고 AS-IS, TO-BE, 근거 로그를 함께 확인합니다.
- 이슈를 바로 다음 차수로 넘기지 말고 개발 수정 중 또는 해결 상태인지 먼저 확인합니다.
